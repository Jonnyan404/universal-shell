主界面布局方案对比

面向「大批量程序管理」的五套布局原型 · 同一份数据、同一套设计语言、可切换 24 / 48 / 120 规模
5 套原型 · 全部可交互
数据字段对齐 workspace_list

当前布局为什么撑不住

01 · 空间
200px 侧栏装不下元信息
名称 + 状态 + 调度归属已挤满两行，端口、版本、分类只能省略。程序过 30 个就只能靠滚动找。
02 · 结构
一维平铺，没有分组层级
分类字段存在于 Program 里却没用起来；同类程序散落在列表各处，无法整组操作。
03 · 操作
批量入口藏在勾选后
勾选框和状态点抢同一行空间，批量条出现时会挤动列表，长列表下选中态难以确认。
04 · 全局
没有「整体健康」视图
只能逐个点开才知道谁异常、谁待更新。异常发现依赖你恰好翻到那一行。

五套方案

方案 A

分组卡片视图

Grouped Cards
按分类分组的卡片栅格，组头可折叠、可整组启停；卡片承载图标、状态、版本、端口与两个高频操作。左侧分类树带计数，是「浏览 + 轻度操作」的均衡解。
一眼识别分组折叠整组操作单屏可见约 12 个
打开原型 →实现成本：低（复用现有卡片样式）
信息密度3.0
导航效率3.0
批量操作2.5
单点深度3.0
全局监控3.0

我的建议

不要只选一个——用「E 总览 + B 管理 + D 检查器」组合

这五套不是互斥的单选题，而是同一份数据的不同投影。真正撑住大批量的关键，是让「发现」和「处置」走不同的界面：

  1. 首页用 E（健康矩阵）：程序再多也能一屏看完，红色方块 + 关注队列负责「告诉你哪里出事了」，这一步不需要任何导航。
  2. 主管理视图用 B（数据表）：真正要改配置、批量启停、按端口/版本比对时，表格的列对齐和 Shift 连选无可替代。
  3. 详情复用 D 的检查器：从表格或矩阵点进去，右侧（或抽屉）直接给概览/配置/调度/日志/更新五个 Tab，避免来回跳页。
  4. A 保留为「分类浏览」模式：对刚导入、还不熟悉 id 的程序，卡片比表格更容易认。
  5. C 只用于异常处置：把它做成「异常」筛选下的临时泳道视图，不要作为主界面——它的横向空间成本太高。
落地顺序建议：先做 B（收益最直接、改动集中在列表区）→ 再抽 D 的检查器 → 最后加 E 作为首页。三者的数据层完全一致，都读 workspace_list，不需要改 shared。

选之前先回答三个问题

你 80% 的时间在做什么？如果多是「批量启停 / 改配置」，B 优先；如果多是「某个程序挂了去查」，D 或 E 优先。
程序数量会到多少？稳定在 20 以内，A 足够；会到 50+，B 是底线；可能到 100+，E 必须有。
主要在桌面还是手机用？桌面选 B/D/E；手机端现有卡片流（阶段 G）已经合适，不必跟着改。
原型说明：五份 HTML 均为独立文件，无外部依赖，可直接双击打开；顶部「规模」下拉可在 24 / 48 / 120 之间切换，用于对比大批量下的信息密度差异。数据为与 workspace_list 字段对齐的模拟数据（id / name / category / state / supervisor / version / latest_version / port / autostart / uptime），交互为前端模拟，不连接真实服务。
